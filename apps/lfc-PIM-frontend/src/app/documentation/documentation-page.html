Comment le PIM est pensé — et comment un simple paramétrage se transforme en collections Shopify. À parcourir onglet par onglet.

POC front-only. Les données vivent dans un seed versionné dans le repo, surchargé par le localStorage du navigateur. Aucun back pour l'instant — la démo tourne depuis n'importe quel poste.

Le PIM est la source de vérité du catalogue. On y décrit les catégories, les régimes de TVA et les produits ; le système en dérive les collections finales, prêtes à être poussées vers Shopify.

« Réduit · 5,5 % », « Normal · 20 % »… Chaque régime est une donnée éditable, et correspond à une collection côté TVA.

Porte les défauts de canaux (par boutique × à emporter / sur place) et deux régimes de TVA. Côté Shopify, elle devient une collection.

Reprend les canaux et la TVA de sa catégorie. On peut override les canaux, en tout-ou-rien, pour ce produit précis.

Ce que voit le client : un rayon en ligne. Générée automatiquement à partir des canaux actifs — jamais saisie à la main.

Trois calques se composent, dans cet ordre, pour produire ce que voit chaque vitrine : la TVA d'abord, puis la disponibilité sur les canaux, puis le rendu utilisateur.

  1. ① TVA — le régime fiscal, hérité par canal (à emporter ≠ sur place).
  2. ② Disponibilité — sur quels canaux le produit est vendu (boutique × mode).
  3. ③ Display user — le rendu final, propre à chaque vitrine.
  4. La composition des trois calques donne l'output d'une vitrine (click & collect public, sur place QR…).

Une feuille n'est pas abstraite : c'est ce que voit le client. Ici, la disponibilité d'une table — catégories dépliables, produits dedans (données live du catalogue).

Technique : elle regroupe les fiches par taux pour la compta et l'export. Jamais montrée au client.

Le catalogue en ligne, rayons publics — la vente à emporter commandée depuis le site.

Click & collect immédiat, commandé depuis une URL custom liée au QR code d'une table.

Une boutique = un emplacement. Il porte ses modes de vente ; le sur place ouvre les tables, et chaque table devient un point de commande click & collect avec son QR. Gérés dans Emplacements (menu).

Chaque emplacement active ses canaux. Click & collect = commande en ligne ; sur place = consommation à table (et ouvre les tables).

Le nombre de tables génère une section click & collect par table. Chaque table a un numéro — verrouillé, car il fait l'identité de son URL.

L'URL dérive de la base : …/commander?table=N, le paramètre table figé sur la table. Un QR par table ; tant qu'il n'est pas généré, pas de QR.

QR réel & scannable. Chaque QR encode l'URL de sa table (…?table=N) via qrcode-generator, rendu en SVG noir sur blanc. L'état « généré / non généré » pilote son affichage.
Push idempotent, SEO-safe. Une fois une collection ou un produit créé, on ne le recrée jamais : on le met à jour par id. Le handle Shopify — donc l'URL, donc le référencement — reste intact.

Le handle est calculé une seule fois, à la création. Modifier le contenu (titre, textes, images, prix) ne le change pas. Le push suit donc un upsert piloté par le binding.

La table de correspondance id + handle. Elle décide create (première fois) vs update (ensuite), et garde le lien vers la bonne ressource Shopify.

Une empreinte du dernier contenu poussé. Inchangée → on saute l'appel. Moins d'écritures, pas de churn inutile côté Shopify.

Si un handle doit vraiment changer, on pose une redirection 301 pour ne pas perdre le jus SEO. Par défaut : on ne touche pas au handle.

Config manuelle, une seule fois. Les tax overrides ne sont pas pleinement pilotables par API : le PIM crée les collections TVA programmatiquement, mais le mapping collection → taux se règle à la main dans l'admin (Réglages → Taxes et droits de douane).
